## 4. R1 — Inventory debt state consistency proof

### Before

MultiItem debt payment could write a contradictory record equivalent to:

```js
{
  unpaid: false,
  inventoryDebtStatus: 'pending'
}
```

The active-debt classifier accepts `unpaid === true OR inventoryDebtStatus === 'pending'`, so the record could continue to classify as debt even though `unpaid` was false.

### After

The existing `InventoryService` now exposes a pure preparation primitive returning the canonical paid state:

```js
{
  unpaid: false,
  inventoryDebtStatus: 'paid',
  paidAt,
  paidDate,
  paidTxId,
  paymentBundleId
}
```

The helper performs **zero Firestore read/write/listener calls**. `processMultiItem()` inserts the patch into its **same existing atomic `writeBatch`**. It does not call `InventoryService.markPaid()` after commit.

Master gate assertion 28 additionally runs the resulting record through `isActiveInventoryDebt(...)` and verifies it is `false`.

### Cache/history invalidation

After a successful atomic commit, the existing path is notified when either:

- a new inventory mutation exists, or
- `invDebtIds.length > 0`.

Therefore a debt-only payment also calls the existing `notifyInventoryMutation(..., { writeThrough: true })` path without adding a listener or read.

## 5. R2 — paidUntil anti-regression proof

MultiItem now normalizes:

- previous/current `profile.paidUntil`
- candidate `lastMonth`

and writes the greater valid YYYY-MM month. No `paidUntil:lastMonth` write remains in the MultiItem canonical mutation.

Mandatory dynamic cases in the H8R2.1 master gate:

- F1: current `2026-12`, collect through `2026-10` → result `2026-12`
- F2: current `2026-08`, collect through `2026-10` → result `2026-10`
- F3: current empty, collect `2026-09` → result `2026-09`

`paidMonths` continues to use `arrayUnion(...packageMonths)` and skipped-month semantics were not modified.

The audit payload now reflects the actual canonical result using previous/candidate/result values instead of falsely asserting that the persisted `paidUntil` is always `lastMonth`.

## 6. R3 — Missing-profile fail-closed proof

### Before

`const profile = allProfiles[name] || {}` allowed an unknown/raw key to reach a merge `set()`, which can create a new profile document.

### After

`processMultiItem()` requires:

```js
const profile = allProfiles[name];
if (!profile) {
  // visible failure; return before atomic plan/write
}
```

No fuzzy/raw-input profile identity fallback is used.

The tuition mutation now uses the existing batch with `batch.update(profileRef, ...)`, not create-if-missing merge semantics. Therefore if the profile disappeared between RAM validation and commit, Firestore fails the whole atomic batch; transaction/inventory/debt writes do not partially commit.

Master assertions 33–35 verify the exact guard, `update()` semantics, and absence of raw-input identity fallback.

## 7. R4 — Quit cache invalidation proof

The existing Quit authority remains the only owner. No listener, reader, event bus, or cache authority was added.

A local `markQuitAuthorityDirty(reason)` function was added inside the existing profiles/Quit ownership module. It changes local completeness/dirty state only.

`StudentStatusCommandBoundary` calls the existing local hook after a successful canonical mutation only when:

- previous profile is quit, or
- resulting profile is quit.

Therefore:

- quit profile `displayName A → B` marks Quit dirty;
- next Quit open performs one existing canonical refresh;
- after completeness is restored, ten repeated opens cause zero additional full reads;
- active-only edit without quit membership does not unnecessarily dirty Quit;
- active→quit and quit→active still invalidate correctly.

The H8R2.1 master gate runs Q1–Q4 dynamically and verifies read count `1 → 1 after 10 reopens → dirty → 2 after refresh → 2 after another 10 reopens`.

## 8. R5 — Attendance pagination fail-closed proof

`AttendanceService.loadByDate()` remains the one daily reader authority.

At entry, if either pagination primitive is unavailable:

- `limit` missing, or
- `startAfter` missing,

it throws an error whose code is:

`attendance/daily-pagination-unavailable`

before issuing any Firestore read.

Dynamic master assertions verify both missing-primitive cases produce the error with **0 reads**. Normal SDK behavior remains unchanged, and the existing 1,501-record dynamic test still loads all data across four pages.
